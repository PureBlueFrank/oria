# Oria V0.3 场景 A 威胁模型

- 版本：V0.3
- 更新日期：2026-09-03
- 适用范围：场景 A 完整 Workflow、写操作 RBAC、双审批、报名/圈品、确认链、选品、C 端投放与通知
- 证据等级：Fixture/Community，本地 SQLite、官方 AsyncSqliteSaver、Mock 企业 Adapter 与合成数据
- 声明边界：不代表真实券、招商、商品库、选品、C 端投放、IM 或企业身份系统已完成 Live 验证

## 1. 安全目标与信任边界

V0.3 在 V0.2 只读 RAG 边界上引入业务写入和外部副作用。核心安全目标是：LLM 只能生成草案并在硬资格候选集内软排序；所有写入必须经过可信 actor/executor、PolicyEngine、冻结业务版本和领域不变量；高风险招商投放与 C 端投放分别审批；外部系统结果最多执行一次，未知结果进入对账而不是盲目重试；Checkpoint、Business Domain/Audit Event 与 Platform Approval/Audit 各自保持独立真相源。

| 边界 | 不受信或可失效输入 | 强制控制 |
| --- | --- | --- |
| LLM/RAG → 领域 Service | 草案、工具参数、文本中的授权声明 | Tool schema、PolicyEngine、EligibilityPolicy、领域状态机重新校验；Repository 不暴露给模型 |
| actor/executor → 写 Tool | 自报角色、跨 tenant ID、恢复时已撤销权限 | 主体来自受信 Context；actor 与 executor 双主体授权；恢复时按当前 policy version 重新鉴权 |
| Platform 审批 → Business 副作用 | 自批、过期审批、参数/checkpoint/policy 变化 | 职责分离；approval 绑定 tool、canonical args、checkpoint、policy version、过期时间和业务版本 |
| Oria → 企业 Adapter | 超时、部分成功、响应丢失、重复恢复 | 先 reserve execution ledger；稳定幂等键；`executing` 超时转 `unknown/reconciliation_required`；不盲目重调 |
| 外部事件 → Graph 恢复 | 伪造、重复、乱序、迟到、错误资源/版本 | 受信 adapter 身份、inbox 去重、wait/resource/version/checkpoint 绑定；事件先持久化再恢复 |
| Platform DB ↔ Business DB | 任一库提交失败、跨库状态短暂不一致 | 各库本地事务写 audit/outbox；禁止伪造跨库原子性；通过幂等投影和对账收敛 |

## 2. 主要威胁与缓解

| ID | 威胁 / 故障 | 当前缓解与可复核证据 | 剩余风险 / 后续门禁 |
| --- | --- | --- | --- |
| V03-TM-01 | LLM 绕过硬资格，直接写入不合格商家或商品 | 商家与商品 EligibilityPolicy 在 LLM 外确定性执行；最终事务再次核对冻结 ProductSnapshot、规则、价格、类目、关键词和可售状态 | 上游真实商品质量与企业主数据仍需独立 Adapter 卡 |
| V03-TM-02 | 活动管理员自批，或复用 launch 审批进行 C 端投放 | `launch_approval` 与 `consumer_publish_approval` 使用不同 action/tool/binding；requester 不能作为 approver；错误角色默认拒绝 | 正式 OIDC/组织目录与撤权传播留 V0.6 验证 |
| V03-TM-03 | 审批后篡改规则、券档、招商范围、素材、选品结果或投放参数 | canonical hash、LaunchPlan 子步骤 hash、checkpoint、policy version 与业务 binding 共同冻结；任一变化使旧审批失效 | 外部系统若不支持强幂等，仍只能进入人工对账 |
| V03-TM-04 | 审批通过后进程退出，恢复时重复执行副作用 | 审批与 checkpoint 已持久化；执行前查 execution ledger；进程重建和重复恢复测试断言每个业务幂等键计数为 1 | SQLite 只证明单 worker；多 worker fencing 留 V0.6 PostgreSQL E-like 卡 |
| V03-TM-05 | 外部系统已受理，但本地 receipt/业务事实尚未落库时进程退出，或 rejected receipt 被丢弃 | ledger 在调用前置为 `executing`；新鲜重放只等待，超时原子转 `unknown/reconciliation_required`，不得重新调用 Adapter；`business_0010` 保留 accepted/unknown/rejected 回执 ID 与脱敏 summary hash | 需要真实企业 Adapter 提供查询/对账接口才能把 unknown 收敛为最终事实 |
| V03-TM-06 | 券已物化但招商发布失败时伪回滚，掩盖真实外部事实 | CouponBatch 保持 ready；仅已验证且幂等的补偿契约可执行，否则 fail-stop 到 reconciliation；每个子步骤独立 ledger | Mock 只证明 Oria 语义，不证明真实券系统可补偿 |
| V03-TM-07 | 商家报名与自动圈品重复、迟到或跨版本，污染选品集合 | `merchant/auto/hybrid` 冻结 join 语义；业务唯一键合并 source；关窗后默认拒绝；允许补报时创建新版本并使下游审批失效 | 真实 webhook 时钟、签名和网络重放留 V0.6 HTTP 验证 |
| V03-TM-08 | 伪造 selection webhook、未授权事件抢占去重 ID，或客户端直接指定 wait/checkpoint | 标准事件 union、受信 adapter executor、inbox payload hash、resource/version/wait 绑定；未授权 envelope 不占用持久去重标识；领取 matched 事件时再次校验 wait 未过期 | 当前是本地 Mock Adapter，未证明企业网关验签兼容性 |
| V03-TM-09 | 未确认商品、无有效券关联或旧 selection version 进入 C 端投放 | 动态确认链完成后才可关联券；submit 使用独立 assortment policy；投放只接受 selected 且 link active 的冻结版本 | 真实选品系统的最终一致性与撤回语义需独立验证 |
| V03-TM-10 | 部分通知失败导致已发布活动被回滚或整批重复通知 | 每个商家通知使用独立业务唯一键、execution ledger 和 dead-letter；通知失败不回滚 ConsumerPlacement；重复执行返回历史 | V0.3 未实现生产级通知重试调度和死信运维界面 |
| V03-TM-11 | Platform/Business 跨库失败被错误描述为整体原子成功 | 两库分别本地事务提交 audit/outbox；测试分别注入回滚并验证无跨库双写；报告显式区分暂态与收敛 | 统一审计投影消费者与跨库告警仍需平台服务化 |
| V03-TM-12 | 黑白名单、销售组织或未授权商家数据进入 LLM、日志、通知 | LLM 只接收公开规则投影与候选白名单；audit/outbox 使用哈希和脱敏 payload；inbox 只保存脱敏 payload 与 hash | 尚未接入真实 DLP/内容分类服务，不得声称生产 DLP 已完成 |
| V03-TM-13 | reducer 冲突被 last-write-wins 吞掉，造成并行分支状态漂移 | `merge_unique` 只允许新增或语义相同重放；同 key 异值抛 `StateConflictError`，冲突 super-step 不接受 | 后续新增并行 state key 必须先定义结合律 reducer |
| V03-TM-14 | 用 Mock 通过冒充企业系统或真实模型验证 | 报告分开记录 F/C/L/E；T08 只关闭 Community Core；T09 与各企业 Adapter 保持独立状态卡 | V0.3 版本“全部通过”仍需要 T09 DeepSeek 必需 Live 卡 |

## 3. T08 故障注入覆盖

| 故障点 | 预期结果 | 证据 |
| --- | --- | --- |
| LaunchPlan 批准后执行进程退出 | 新进程从持久审批继续；券与招商发布各执行一次 | `test_approved_launch_survives_process_rebuild_before_first_side_effect` |
| 券外部成功但 saga checkpoint 未推进 | 读取 materialize 历史后继续招商发布；不重复物化券 | `test_saga_resumes_from_unadvanced_checkpoint_using_child_ledger_history` |
| 选品提交外部受理后、本地成功落账前退出 | execution 从 executing 超时转 unknown；Adapter 调用数保持 1 | `test_process_exit_after_external_acceptance_never_blindly_reinvokes[submit_assortment]` |
| C 端投放外部受理后、本地成功落账前退出 | 同上，进入人工对账，不盲目重投 | `test_process_exit_after_external_acceptance_never_blindly_reinvokes[publish_consumer_placement]` |
| 商家通知局部失败 | 已发布 placement 保持 published；成功通知与 dead-letter 各自落账 | `test_partial_notification_failure_does_not_roll_back_consumer_placement` |

上述测试只模拟进程边界和本地持久语义，不把内存 Mock Adapter 的调用结果描述为真实外部系统回执。V0.6 还必须以 PostgreSQL 双 worker、lease epoch 和 fencing token 复验并发接管。

## 4. 数据、审计与保留

- Workflow checkpoint 保存恢复所需状态，不作为业务或合规事件真相源；Business/Platform audit/outbox 分别与所属状态同事务提交。
- 报告只保存命令、测试计数、哈希、状态和脱敏断言，不保存密钥、原始提示词、黑白名单、销售组织或隐式思维链。
- 集成 inbox 不保存 raw body；只保存标准化脱敏 payload、payload hash、可信 adapter/subject 与处理状态。
- `unknown` 和 dead-letter 是必须保留的业务事实，不能删除失败记录或通过重跑挑选成功结果覆盖。
