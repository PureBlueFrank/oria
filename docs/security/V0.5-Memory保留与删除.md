# V0.5 Memory 保留与删除说明

- 适用版本：Oria V0.5 Community
- 更新日期：2026-09-10
- 适用数据：用户明确保存的跨会话 Memory，以及可能包含其历史副本的 checkpoint/备份

## 1. 保存语义

长期 Memory 默认不写入。只有用户或受控工具显式提交 `opt_in=true` 时，`save_memory`/`PersistentMemory.save_fact` 才会按 `(tenant_id, subject_id)` namespace 保存。会话内历史、滑窗摘要和事实账本属于 checkpoint 上下文，不因摘要生成而自动转为长期 Memory。

写入前执行 namespace 授权、内容长度、敏感度、时区和到期时间校验，并对常见凭证、邮箱和电话模式脱敏。检索结果始终标记为 `trust_level=untrusted_data` 和 `authority=non_authoritative`；不得用它们授权工具、覆盖 system 规则或替代业务系统事实。

## 2. TTL 与主动保留

- `expires_at` 是可选、带时区的绝对时间。提交时必须晚于当前时间。
- 达到 `expires_at` 后，该项立即从 `search`、`view` 和 `export` 的 active 查询中排除，不再注入新请求。
- V0.5 没有为 Memory 强制统一默认 TTL；未提供 `expires_at` 的项保留到授权主体删除或当前 Community 数据目录被明确停用。产品部署应根据数据分类提供有限 TTL，不得将“未配置”解释为法定无期保留依据。
- V0.5 Community 的 TTL 是逻辑过期门禁，不是后台物理清理任务；过期行可留在主库，直到显式删除或数据目录按运维周期停用。

## 3. 删除传播

已授权的 `memory delete`/`PersistentMemory.delete` 在当前 active Community 存储上执行以下传播：

1. 在同一 platform DB 事务中将 `memory_items.content` 清空，将记忆标记为已删除，并清除可注入的 provenance/confidence/sensitivity/score 值。
2. 在同一事务中删除对应 `memory_embeddings` 向量投影。
3. 提交后失效该 tenant + subject 的进程内搜索缓存。当前 Community 没有分布式缓存 Adapter；未来引入时必须实现并验证跨实例失效。
4. 删除返回后，当前 active store 的 `search`、`view` 和 `export` 均不得再返回该项。

正文清空、向量删除、审计写入使用一个 SQLite 事务；事务失败不得报告删除成功。当前断言见 `tests/security/test_v05_memory_boundaries.py::test_delete_clears_body_vector_cache_and_writes_only_redacted_audit`。

## 4. 删除审计

删除审计用于证明操作发生，不用于保留被删除内容。`memory:deleted` 事件仅保留：

- tenant、操作者 subject ID、操作时间和 correlation ID；
- Memory 对象 ID 及不可逆 `object_hash`；
- Policy version、允许决策和已脱敏的参数 hash。

事件 payload 不得保留被删除正文、检索 query、原始提示词、凭证或 PII。V0.5 Community 没有独立的审计过期清理器；脱敏删除事件随 platform DB 保留，直到数据目录停用或后续部署策略到期。

## 5. Checkpoint 与备份残留

Memory 检索结果可能已出现在历史消息或 Tool observation 中，并随 LangGraph checkpoint 保存。Memory 删除不扫描或改写历史 checkpoint，因为机械改写可破坏工作流恢复和审计一致性。V0.5 Community 不会由 Oria 自动创建外部备份，也没有 checkpoint 自动到期/清理任务；本地 checkpoint 随当前 Community 数据目录保留，直到该目录被授权操作者明确停用。因此：

- 删除后的新 Memory 查询会 fail closed，但不能由此声称历史 checkpoint 或任意外部备份已“立即物理清零”。
- V0.5 Community 配置不得作为有法定删除时限的生产保留方案；这是 Enterprise/上线前门禁，不是已完成能力。
- 启用任何生产 checkpoint 归档或备份前，部署方必须根据数据分类公开一个有限的最长保留期，配置到期清理，并用可恢复的测试备份验证。
- 备份在保留期内使用访问控制和加密保护，到期后由存储后端清理；后端介质的最终回收时间应另行声明。
- 从删除前备份恢复时，必须先在隔离环境中恢复，再从不随该快照回滚的删除请求/墓碑记录重放删除，重建向量并清理缓存；在该步骤完成且通过 search/view/export 及底层投影核查前，不得对外提供恢复数据。

当前 V0.5 Community 尚无外部删除墓碑库、生产备份 Adapter 和恢复后重放验证卡，因此上述恢复流程是后续生产接入的强制条件，不是 V0.5 已验证声明。

## 6. 用户操作与验证边界

用户可通过 `memory view`、`memory export`、`memory delete` 查看、导出和删除自己 namespace 中的 active Memory；所有操作继续通过 PolicyEngine 鉴权。导出不包含 tenant/subject 内部键，但仍可含用户主动保存的脱敏文本，应按 internal 数据保护。

当前自动化证据只支持 Fixture/Community/Security 级别：本地 SQLite 主库、向量投影与进程缓存的生命周期可验证。它不支持 Live 模型、Enterprise 存储、外部备份或合规删除 SLA 声明。相关风险与代码证据见 [V0.5 威胁模型](V0.5威胁模型.md) 和 [ADR-012](../adr/ADR-012-memory-as-tool-and-long-term-memory.md)。
